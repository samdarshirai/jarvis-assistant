## Multi-tenant BYOK (merged; spec `docs/superpowers/specs/2026-10-20-multi-tenant-byok-design.md`)
Friends are added by hand and bring their own LLM key (any OpenAI-compatible endpoint); Deepgram and Tavily keys are operator-set (`JARVIS_DEEPGRAM_API_KEY`, `JARVIS_TAVILY_API_KEY`), shared by all users; no per-user storage or UI. Cap 100 users (Google's unverified-app cap), enforced by the CLI.
- `users.py`: `User`, `UserStore`, `SecretStore` (Fernet; names `llm_base_url, llm_key, model_fast, model_strong`), `ensure_owner` (first start: creates user #1 from `JARVIS_OWNER_EMAIL`, adopts rows with `user_id IS NULL`, copies operator env keys into the owner's secrets, renames thread `owner` -> `user:<id>`, one transaction, idempotent), `thread_id(uid)`. CLI: `python -m jarvis.users add <email> [--owner] [--tz IANA] | list | disable | enable | delete [--yes]`. `disable` revokes the user's devices (the owner is refused); `delete` only prints row counts unless `--yes`, then cascades data and conversation. Emails are stored lowercased.
- `tenant.py`: `Tenants(pool, settings, saver, max_size=max(32, MAX_USERS))` is an LRU (sized to the user cap, so the scheduler's scans never evict) of `UserRuntime` (user, secrets, audit, memories, notes, proactive, calendar/tasks/gmail clients, registry, llm, graph, lock, tz). `get(uid)`, `invalidate(uid)` (after any key or Google change), `lock(uid)` (per user, never evicted). `auth_runtime(devices, tenants, authorization)` checks the bearer token and re-reads the user row, so a CLI `disable` takes effect on the next call (401). `graph` is None until an LLM key is set (`llm_ready`); chat then answers 409 `needs_setup`.
- `signin.py`: `POST /auth/start {challenge}` stores sha256(verifier) under a random nonce (10 min TTL) and returns the Google URL (state = nonce). `GET /auth/callback` exchanges the code and requires a verified email that is on the list and enabled, and binds `google_sub` once (a different Google account, or a sub already used by another user, is refused). It stores the Google credentials, creates a device, keeps its encrypted token under a one-time finish code and redirects to `jarvis://signin?nonce=<nonce>&code=<code>`. `POST /auth/claim {nonce, verifier, code}` returns `{token, needs_setup}` once; a wrong verifier or code is a 401 that keeps the attempt. The token never sits in a URL, and the finish code stops someone collecting a token for a sign-in another person approved.
- `keys.py` + `llm.py`/`llm_check.py`: `GET/PUT /me` (email, tz, `setup` flags, last 4 of keys only), `PUT /settings/llm {base_url, api_key, model_fast, model_strong}`. The LLM PUT makes one test call per configured model and stores nothing unless all pass; failures are 422 `{error, model}` with `bad_url`, `no_models`, `rejected_key`, `out_of_credit`, `model_not_found`, `unreachable`. Base URLs must be public hosts (rechecked per request). Every change calls `invalidate` and writes an audit row without key values.
- Onboarding wizard (Flutter, spec decision 6): Connect Google → name → AI key → Ready. `/me.setup` (`google`, `llm`) determines the first missing step on sign-in/restart and gates existing installs too. The AI key is tested before saving. Ready rechecks setup before opening the app. No Skip; Back, visibility toggles and inline save/error feedback are available. Settings reuses the forms;  No token is baked into the APK.
- Voice uses the operator's `JARVIS_DEEPGRAM_API_KEY`; if it is unset the server sends `{"type":"error","code":"needs_deepgram"}` then closes 4403 (`needs_llm` likewise). Startup (`init_schema`) deletes any `deepgram_key`/`tavily_key` rows left in `user_secrets`. Proactive jobs run per enabled user and skip the LLM when there is none. Alerts reach friends as push only; Telegram is owner-only. The user-facing capabilities list (`jarvis_app/lib/capabilities.dart`) is unchanged: no tool or job was added.

### Open items (deferred risks)
- No rate limit on `POST /auth/start` (writes a row, mints a Google URL): add a per-IP limit in Caddy.
- Friends see Google's unverified-app warning once; 100-user cap. Rules checked 2026-10-20 (see `docs/DEPLOY-RAILWAY.md`); production refresh-token lifetime not confirmed from Google's page (ACCEPTANCE row 96).
- Google's one-time auth code appears in access logs on `/auth/callback?code=...`: filter the query string.
- Unclaimed device rows: a finished sign-in the app never claims leaves a `devices` row (the encrypted attempt is purged after 10 minutes; the device stays until revoked, disabled or deleted).
- Retired runtimes (evicted or invalidated) are held until restart: one LLM client leaks per eviction or key change.
- Mail watch (auto-creating calendar events from booking emails) runs for the OWNER only: its Undo is a Telegram button and the app has none, so friends get no auto-created events. To enable for friends, add Undo to the app and set `FRIEND_MAIL_WATCH = True` in `proactive/scheduler.py`.
- The 100-user cap check is count-then-insert and can overshoot under concurrent adds (CLI only).

## Safety invariants (do not break)
All invariants below hold per user: each user has their own runtime, lock, thread (`user:<id>`), audit rows, tokens and keys; read "owner" as "the user". Telegram serves the owner only. Nobody falls back to the operator's env keys.
- Every side effect goes through the graph's `interrupt()` confirmation gate (in the graph, not the prompt) (one bounded exception: see the next bullet). A mixed step (confirm-gated + non-gated call) never interrupts: the gated call is refused "propose it again by itself".
- The one bounded exception: events auto-created from new email are written by plain code (model output only passes `validate_extraction`; fixed description; deterministic sha1 event id; dedupe; rolling-24 h cap; audit rows `auto_event_attempt`/`created`/`undone`; Telegram notice with Undo). Undo deletes only ids in `auto_events`, outside the lock and the graph.
- Sub-project 6: shopping adds are ungated, but `confirm_after_untrusted` gates them whenever untrusted email or web text was read this turn or is in the history window (a mixed step still refuses the gated call). Invites are only sent after confirmation (a tap in Telegram, or a spoken yes on voice) and the card lists every address; `find_contact` reads headers only. `sendUpdates="all"` is used only when attendees are added, so the update card also names the EXISTING guests who get an update email (an invitee already on the event is reported as "none new").
- Confirm taps/buttons carry the interrupt id; stale/bare taps get "Already handled."; new text while a confirmation is pending is refused (Telegram re-offers the card with buttons; voice re-presents it).
- Voice may resume a confirmation only by a bare yes/no (`voice/confirm.py`, plain code) AND only for the interrupt that session itself presented (`VoiceSession.offered`); a spoken "yes" never confirms `send_draft` (tap only; a spoken "no" still cancels).
- One `asyncio.Lock` shared by Telegram and voice serialises "read pending -> decide -> ainvoke" on the user's single thread `thread_id: "user:<id>"` (`UserRuntime.lock`, one per user, never shared; the old thread `owner` is renamed on migration). A voice graph step is shielded: barge-in/disconnect/replacement abandon waiting but never cancel a running step (so a confirmed write is always audited).
- Untrusted wrapper is per-tool (`untrusted_email` / `untrusted_web`); research output is redacted in the audit log; `fetch_page` refuses non-global addresses on every hop and pins the connection to the checked IP; `remember` is gated so a page cannot plant a memory silently.
- Untrusted email and web text is data: wrapped, redacted in audit, and a write proposed after reading either carries a visible warning (also spoken by voice). Audit log purged at 90 days; no audio/transcripts are stored or audited.
- Device token: sent as `Authorization: Bearer`, checked in constant time against a SHA-256 hash, connection closed before accept on a bad token; one live voice session (new connection replaces the old).

## Call a contact (merged, 2026-10-23; spec `docs/superpowers/specs/2026-10-23-call-contact-design.md`)
Voice "call Mom" runs the new phone tool `call_contact`: WhatsApp voice call via the call row WhatsApp adds to synced contacts (native bridge `callOnWhatsApp`), else a phone call (`ACTION_CALL` if CALL_PHONE is granted, else `ACTION_DIAL`). New client frame `action_result` (phone to server) reports only problems: ambiguous (names + last 4 digits only), not found, no contacts permission, error.
